リードエンジニアとしてインフラ構成の壁打ちをする。要件を詰め、構成図と概算見積の骨子まで固めることがゴール。

一問ずつユーザーとやり取りする対話なのでサブエージェントには委譲しない。構成選定は見落としのコストが高いため、開始時にセッションのモデルを Opus に切り替えるよう提案する。

## 1. 正本を読む

company-knowledge スキルの手順でルートを解決し、以下を読む。技術選定のデフォルト（クラウド / PaaS / DB / ストレージ / IaC / 監視）と環境構成は正本の記述に従い、正本に無い内容を社内標準として断定しない。

- `infra/README.md` — 選定方針と、構成図・見積書サンプルへのリンク
- `infra/basic_architecture.md` — スタック・環境構成

## 2. 壁打ち

kabe スキルと同じ進め方（質問は一つずつ・必ず推奨回答と理由を添える・調べれば分かることは聞かない）。確認する観点（案件に応じて取捨選択）：

- 解決する課題とアプリケーション構成（バックエンド / フロントエンドの技術スタック）
- 顧客環境の制約（指定クラウド・既存契約・セキュリティ要件）
- トラフィック・データ規模と成長見込み
- 予算感（月額オーダー）と運用体制（誰が面倒を見るか）
- DB の選定（アプリケーションプラットフォーム内包か、単体マネージドか）
- オブジェクトストレージ・キャッシュ・非同期処理の要否
- 環境構成（正本のスタック構成を基本に増減）
- 監視・アラートの通知先

推奨回答は正本のデフォルトを第一候補にし、外す場合は理由を明示する。

## 3. 構成図の反復（Mermaid）

検討中の構成は Mermaid でチャットに提示し、フィードバックを受けて反復する。この段階では描き直しの速さを優先し、清書はしない。合意したら、構成まとめ・Mermaid・決定の経緯を markdown ファイル（合意サマリ）として保存する。

## 4. 構成図の清書（draw.io）

構成に合意したら、draw.io 形式で清書する。フォーマットは正本のシステム構成図サンプルを参考にする。

1. `.drawio` ファイルを生成する。クラウドベンダー公式のアイコンシェイプ（AWS なら AWS 2019 シェイプ等）を使い、クラウド境界・VPC・環境などのグルーピングと、利用者からの流れを表現する。公式シェイプが無いプロバイダ（Vercel / Fly.io / Supabase / Cloudflare 等の PaaS）は、ブランドカラーのボックスとプロバイダ境界の破線枠で表現する
2. draw.io CLI（`/Applications/draw.io.app/Contents/MacOS/draw.io` 等）があれば `-x -f png` で PNG をエクスポートし、**生成した画像を自分で読み込んで目視検証**（アイコン・ラベル・矢印の重なりや欠け）してから提示する。崩れていれば XML を修正して再エクスポートする
3. CLI が無ければインストールを提案し（macOS: `brew install --cask drawio`）、不可の場合は `.drawio` ファイルを成果物として、draw.io（app.diagrams.net）で開いて PNG エクスポートする手順を案内する

`.drawio` ファイルを正として必ず残す。人間の微調整や顧客指定フォーマットへの対応はこのファイル上で行う。

## 5. リソース一覧と概算見積の骨子

リソース一覧（サービス / スペック / 台数 / 環境）と月額の概算オーダーを表で提示する。精緻な金額ではなく桁感の共有が目的。正確な見積は正本のインフラ見積書サンプルに沿って人間が清書する。

## 6. ISSUE 化

十分に深まったら issue スキルに接続して ISSUE 化する。成果物3点をアップロードする：

1. 合意サマリ（Mermaid 含む markdown）— ISSUE 本文に埋め込む
2. 清書画像（PNG。`.drawio` も添付またはリポジトリに保存）
3. 概算見積の骨子（markdown）

構築は infra-build スキルが引き継ぐ。
