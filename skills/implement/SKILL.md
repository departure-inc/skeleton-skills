# /implement <issue番号>

ISSUE を読み、方針承認の 1 回だけ確認を挟んで、実装・検証・報告まで自律的に進める。

## 手順

1. **ISSUE 取得**
   `gh issue view <番号> --json number,title,body,labels,comments`
   （リポジトリはカレントディレクトリから自動検出される）

2. **コンテキスト把握と種別判定**
   AGENTS.md / CLAUDE.md を読む → 技術スタックとテスト・lint・型チェックのコマンドを検出する → 関連コードと既存の類似実装を調査する。
   ラベルが `bug` / `chore`、本文に `# 修正方針` 見出しがある、または本文が不具合テンプレート形式なら **保守**、それ以外は **新機能** として進める。

3. **方針の提示（唯一の確認ポイント）**
   - **保守**：ISSUE の「修正方針」に従う。書かれていなければ、変更範囲が最も小さい方針を選ぶ（既存コードの改修に限らず、類似実装の流用・呼び出し元の差し替え・設定やデータでの対処なども比較する）。提示するのは方針 1〜3 行・変更ファイル一覧・再現テスト 1 本（Given/When/Then）だけ。バッチ・コマンド・運用対応などで自動テストでの再現が割に合わない場合は、テストの代わりに手動の確認手順（修正前の失敗と修正後の成功をどう確かめるか）を示す
   - **新機能**：実装概要（1〜3 行）・変更ファイル一覧・bdd スキルの記述ルールに従ったシナリオを提示する
   - 仕様の曖昧さがあれば、推奨案を添えてここでまとめて確認する

   新機能のうちエッジケースの見落としコストが高いもの（権限・データ整合性・課金など）に限り、2〜3 の調査とシナリオ設計を Agent ツール（`model: opus`）に委譲し、その提案をここで提示してよい。4 以降の実装は本体（セッションのデフォルトモデル）がそのまま進める。

4. **実装（Red → Green → Refactor）**
   シナリオをテストとして自動化して Red を確認 → 実装で Green に → Refactor（保守で手動確認に代えた場合は、その手順で修正前後を確かめる）。プロジェクトの規約と既存パターンに従う。
   - Refactor するのは今回自分が書いたコードだけ
   - ISSUE にない抽象化・共通化・依存追加・設定項目の追加はしない
   - 気づいた改善点は手を付けずにメモし、報告に回す
   - 保守では既存コードの書き換えを最小にする。その結果生じた重複や暫定対応は、報告に「後で整理する候補」として書く

5. **検証と報告**
   検出したテスト・lint・型チェックをすべて実行し、次を報告する：変更ファイル一覧と差分規模・実行結果・残タスク・気づいたが対応していないこと（別 ISSUE 候補）。

## 中断して報告する条件

- 承認後に仕様矛盾など想定外の事象が起きた
- 差分が提示した変更ファイル一覧を大きく超えそう（保守では一覧外の実装ファイルに手を入れる時点で。テスト・fixture・lockfile など付随する変更は除く）、または保守で既存コードを大きく書き換える必要が出てきた（方針を変える前に相談する）
