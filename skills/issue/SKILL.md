ユーザーと壁打ちして内容を詰め、合意した内容を GitHub ISSUE として作成する。

一問ずつユーザーとやり取りする対話なのでサブエージェントには委譲しない。kabe から続けて呼ばれた場合はセッションのモデルをそのまま引き継ぐ。

## 0. 種別判定（最初に必ず）

会話・既存コード・AGENTS.md から種別を推定し、推奨付きで一言確認する。

- **新機能**：新しい振る舞いを足す → §1 へ
- **保守**：不具合修正・既存機能の小さな変更・運用対応 → §M へ

kabe・infra-design など設計系スキルから続けて呼ばれた場合は判定を省き、新機能として扱う（インフラ構築も含む）。それ以外で迷ったら保守として扱う。途中で見立てが変わったら、どちらの方向にも切り替えてよい（保守で始めて設計が必要と分かった／新機能で始めて小さく済むと分かった、など）。

## M. 保守モード

方針：**最小の変更で確実に直す。** 工数と影響範囲を小さく保つことを優先し、設計の改善は目的に含めない（必要なら別 ISSUE にする）。

1. 先にコードとログを調べ、原因の当たりをつけてから聞く。質問は原因確認と方針選択の 2〜3 問まで
2. 修正方針の候補を **2〜3 案、規模感（変更ファイル数・既存コードへの影響）付き** で出し、工数と影響範囲が最も小さい案を推奨する。既存コードの改修だけに視野を狭めず、状況に応じて次のような方法も比較する（例であり、必須ではない）：
   - 動いている類似実装を流用し、差分だけ書き換える
   - 呼び出し元（コマンド・ジョブ・ルーティング）の差し替えで済ませる
   - 設定・データ側で対処する
3. 既存コードの大幅修正・共通化・リファクタを選ぶ場合は、より小さい案では足りない理由を本文に書く
4. 本番のコマンド・設定の変更やデータ修正を伴う案は、その旨を修正方針に明記する（実行はこのスキルでは行わず、deploy スキル等の手順に委ねる）

本文（`.github/ISSUE_TEMPLATE/` に種別に合うテンプレート（不具合なら `bug.md` など）があればその見出しを優先し、下記の不足分を足す）。不要なセクションはスキップする（運用対応・小変更なら「発生環境」「再現手順」は省いてよい）。`# 修正方針` は implement が保守と判定する目印になるので省かない：

```
# 概要
# 発生環境
# 再現手順
# 期待する動作と実際の動作
# 原因
# 修正方針
[採用案と、退けた案を一行ずつ]
# やらないこと
[今回は手を付けない改善・リファクタ・関連不具合]
# 完了条件
```

ラベルは `bug`（不具合）または `chore`（運用・小変更）。

## 1. 壁打ち（新機能）

「どんな機能を作りたいですか？」から始め、**一問ずつ・必ず推奨回答付き**で設計を詰める。

- 先にプロジェクトの技術スタックと既存コードを調べ、質問と用語をそのスタックに合わせる
- コードベースを調べれば分かることは質問しない
- 既存の仕組みで足りるなら新しい仕組みを作らない案を推奨する

確認する観点（機能に必要なものだけ。全部を聞かない）：
WHY（解決する課題）／データ設計（構造・型・制約）／ドメインロジック／API・ルーティング／認証・認可／UI／非同期処理・外部連携／削除時の連鎖挙動／完了条件

## 2. ISSUE 本文生成（新機能）

合意が取れたら GFM で本文を生成する。`.github/ISSUE_TEMPLATE/` に機能用のテンプレート（`feature.md` など）があればその見出しを優先し、下記の不足分を足す。不要なセクションはスキップする。

```
# WHY
[課題と価値]

# WHAT
* [ ] [実装タスクのチェックリスト]

# 設計
[概要／データ設計／API／UI など、壁打ちで合意した設計判断。
コードは方針が伝わる最小限にとどめる]

# やらないこと
[今回のスコープ外]

# 完了条件
[何ができれば実装完了か]
```

## 3. ISSUE 作成

本文を出力後「このまま ISSUE を作成しますか？」と確認し、許可を得てから実行する。

付けるラベルが存在するか先に `gh label list` で確かめる。無ければラベルなしで作成するか、ラベルを作るかをユーザーに確認する。ラベルなしで作る場合は `--label` オプションごと外す。

```bash
gh issue create --title "[タイトル]" --body "[本文]" --label "[feature|bug|chore]"
```
