# /deploy [環境]

リリース対象の差分とリスクを洗い出し、stg までは自走で反映する。本番はリスクサマリを提示し、明示承認を得てからのみ実行する。

## 手順

1. **デプロイ方式の検出**
   日常のリリース操作は Makefile に集約されている前提なので、まず Makefile のターゲット（`make release` 等）を探し、あればそれを使う。無い場合のみ GitHub Actions / `fly deploy` / Vercel / `terraform apply` 等を直接特定し、AGENTS.md / CLAUDE.md・CI 設定・infra ディレクトリを調査する。Makefile が無いプロジェクトでは infra-build スキルでのターゲット整備を提案する。

2. **差分とリスクの洗い出し**
   - リリース対象の差分: `git log` / `git diff`（前回リリースタグ・環境ブランチとの比較）
   - DB migration の有無と内容（破壊的変更・ロック・後方互換性）
   - 環境変数・シークレットの追加/変更の有無
   - インフラ差分がある場合は `terraform plan` 等で反映内容を確認する

3. **ロールバック手順の提示**
   反映前に切り戻し方法を確定させる: 直前バージョンへの再デプロイ手順、migration のロールバック可否、切り戻し不能な変更（データ削除・カラム削除等）の明示。

4. **stg までの反映（自走）**
   dev / stg へは差分確認後にそのまま反映し、結果（デプロイログ・ヘルスチェック）を報告する。失敗時は原因を調査して報告し、勝手にリトライを繰り返さない。

5. **本番反映（承認ゲート）**
   以下のリスクサマリを提示し、**ユーザーの明示承認を得てからのみ実行する**：
   - 顧客影響（ダウンタイム・機能変更・データ影響）
   - 切り戻し手順と所要時間
   - 反映タイミングの妥当性（時間帯・営業日・顧客の利用ピーク）

   senpai の予防レビュー観点（顧客影響・切り戻し・タイミング）で懸念があればここに添える。senpai の常時検知と重なっても別人格は立てない。

6. **デプロイ後の検証**
   ヘルスチェック・主要導線の疎通・監視（Datadog 等）のエラー有無を確認し、結果を報告する。

## 注意

- 本番の migration・データ修正を伴う場合は、承認前に必ず単体で影響を提示する
- 本番反映の失敗時は追加変更で即修復しようとせず、まずロールバック判断をユーザーに仰ぐ
