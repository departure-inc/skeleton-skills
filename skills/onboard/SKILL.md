# /onboard [パス|リポジトリURL]

初見のリポジトリを、既存ファイルを読むだけで「何のシステムで・どう変更すればよいか」が分かる状態まで引き上げる。対象未指定ならカレントリポジトリ、URL 指定なら clone してから始める。

成果物は**チャットへのオンボーディング出力**。ファイルには書き込まない。

**このスキルは調査だけを行い、実行はしない。** 依存インストール・ビルド・コンテナ起動・テスト・lint の実行は含めず、すべて既存ファイルからの読み取りで組み立てる。

**リポジトリ固有の知は AGENTS.md、社内横断の規約・設計標準は company-knowledge の正本。** どちらに属するかを常に区別し、正本の内容をリポジトリに複製しない。

## 手順

1. **既存ドキュメントの確認（重複調査を避ける）**
   AGENTS.md / CLAUDE.md / README / docs/ / ADR を読む。README はルートだけでなくサブディレクトリにもあるので `git ls-files | grep -iE 'readme|\.md$'` で洗う（デプロイ手順が `infra/README.md` にだけ書かれている、といったことが起きる）。
   同時に**鮮度を疑う**: 最終更新日、取り消し線や「旧」表記、参照先ファイルの実在。書いてあることを鵜呑みにせず、手順 5 で設定ファイルの実態と突き合わせる。

2. **外形の把握**
   - 言語・フレームワーク・パッケージマネージャ（マニフェストから）
   - ディレクトリ構造とエントリポイント
   - 依存サービス（DB・キャッシュ・外部 API）を compose ファイル・`.env.example`・設定から
   - 規模感（`git ls-files | wc -l`、主要ディレクトリのファイル数）

   広く当たりをつける探索は Explore / Agent ツールに委譲し、結論だけ持ち帰ってよい。全ファイルを読もうとせず、エントリポイントから使われている順に辿る。

3. **ドメインの把握**
   - モデル・スキーマ・migration から中心エンティティとその関連
   - ルーティング・API 定義から主要ユースケース
   - 英語の識別子と日本語の業務用語の対応（用語集の種になる）

   中心エンティティ 5〜10 個の関連を Mermaid の ER 図に描き、理解が合っているかを確認する。
   スキーマ定義や migration が無い構成（ドキュメント指向 DB・独自 ORM・スキーマレス）では、モデルクラスの属性定義や実際のクエリから関連を推定し、**推定であることを明記する**。関連が読み取れない場合は ER 図に固執せず、主要エンティティの箇条書きに切り替える。

4. **暗黙規約の抽出（ここが最も価値が高い）**
   README に書かれていない「全員が従っているが明文化されていないこと」を拾う。
   - 直近 30 件程度のコミット・PR の傾向（コミットメッセージ規約・ブランチ運用・レビューの粒度）。**その 30 件が何か月分かも見る**（稼働頻度は引き継ぎの温度感そのもの）
   - lint / formatter / CI 設定が強制しているルール。設定が無いこと自体も規約（レビューで人力担保されている）
   - 既存コードの実装パターン（層の分け方・エラー処理・テストの書き方と配置・命名）
   - 不自然に見えるが全体で守られている書き方（理由を推測で断定せず「未解決の疑問」に回す）

   引き継ぎ案件では地雷も同時に棚卸しする。
   - 失敗・skip されたままのテスト、CI の状態
   - EOL / 大きく遅れた依存、**未マージのまま溜まった依存更新 PR・dependabot ブランチ**（セキュリティ更新が放置されている合図）
   - TODO・FIXME の密集箇所、長期間誰も触っていない重要ファイル
   - リポジトリに混入したデータ・バイナリ・認証情報

   影響が大きそうなものは senpai の相談対象として挙げる。

5. **開発コマンドの棚卸し（実行はしない）**
   Makefile・`package.json` の scripts・`docker-compose.yml`・Dockerfile・CI ワークフロー・タスクランナー設定から、次を**出典ファイル付きで**抜き出して一覧にする。
   - 起動 / ビルド / テスト / lint / 型チェック / migration / seed のコマンド
   - 前提条件（ランタイムのバージョン、必要な環境変数、依存する外部サービス）を `.env.example`・Dockerfile・compose から

   このとき **README の記述と設定ファイルの実態の食い違いを指摘する**。ここが静的調査で最も価値の出る箇所。
   - README のコマンドが Makefile / scripts に存在しない、名前が変わっている
   - README にない手順を CI だけが知っている（CI のジョブ定義が実質の正しい手順）
   - compose のサービス名・ポート・バージョンが README の記述とずれている

   コマンドは実行していないので、一覧には**未実行（要確認）**であることを明記する。実際に動かす必要が出たら、ユーザーの判断で別途実施してもらう。

6. **オンボーディングの出力（成果物）**
   次をまとめてチャットに出力する。ここで完了。
   - 30 秒サマリ（何のシステムか・誰が使うか・中心となる 3 概念）
   - 構成図（Mermaid）と主要ディレクトリの役割
   - 開発コマンド表（起動・テスト・lint・型チェック・migration）と、各コマンドの出典ファイル
   - 暗黙規約リスト
   - 地雷・未解決の疑問（人に聞くべきこと）

7. **AGENTS.md への反映（任意・依頼された場合のみ）**
   自分から書き込みにいかない。出力を残したいとユーザーが希望したときだけ、リポジトリルートの AGENTS.md に追記する（無ければ作成）。既存の記述は消さずにマージし、推測は「要確認」を付けたまま残す。
   出力の分量が多い場合に限り、末尾で「AGENTS.md に残すこともできます」と一度だけ添えてよい（繰り返し勧めない）。

## 注意

- 事実と推測を混ぜない。根拠（ファイルパス・コミット）を示せないものは慣習として断定せず「未解決の疑問」に置く
- 観測した慣習は、そのリポジトリでの傾向として書く。社内標準の話にすり替えない（正本が要るときは company-knowledge を使う）
- 依存インストール・ビルド・起動・テスト・lint を自分で実行しない。動作確認が必要なら、その旨を「未検証」として報告に残す
- `.env` の実値・鍵・接続情報を AGENTS.md や会話に書き写さない
- 秘匿情報や顧客固有の事情に踏み込む前に、対象リポジトリを読んでよい立場かを確認する
- 理解が済んだら kabe（設計壁打ち）・implement（実装）へ引き継ぐ
